The framing

Three questions, already half-answered

masova-enterprise-fleet already enforces a propose-then-approve rule for its eight agents. What's missing is naming and closing the loop on the other two Know-Your-Agent pillars — the same three the track's own rubric asks for under different names.

PILLAR 01

Who is behind this agent?

Registry + per-agent identity. Today: one shared trigger key, no discoverable catalog. The clearest gap.

PILLAR 02

What is it allowed to do?

Policy gate + ActionProposal model. Already real — proposal_store.py, idempotency, manager approval. Strongest pillar today.

PILLAR 03

Is it behaving right now?

Reasoning-chain audit + guardrails. Partial: metrics and a rationale field exist; no structured trace, no input/output screening yet.

Market & regulatory framing

Europe-centered, deliberately

The demo runs against a Paris 11e store (DOM011, Oberkampf, EUR pricing in cents, matching the platform's real integer-minor-units convention) rather than the platform's Indian-market default data. Paris is an EU capital with a dense restaurant market — GDPR and EU AI Act still apply. The same three KYA pillars read onto EU AI Act transparency, human-oversight, and risk-tiering language.

Where GDPR shows up as real payload, not decoration

  • churn-prevention win-back proposal surfaces an excluded-for-consent count (Art. 6(1)(a) lawful basis) rather than silently dropping those customers
  • kitchen-coach reports aggregate station metrics only — no individual staff scoring in the payload, avoiding workplace-surveillance characterization
  • review-response personalizes replies with staff first name only, minimizing personal data in a public-facing draft

Where the platform's own design already agrees

  • Real Refund lifecycle has no distinct APPROVED state — approval flows straight into execution, a two-phase gate already native to the platform, not invented for this pitch
  • Real PurchaseOrder carries requestedBy/approvedBy/rejectionReason — human-approval-before-write is a pattern the platform already expects, masova-enterprise-fleet's proposal gate mirrors it rather than bolting it on

Build order

Seven phases to a submitted entry

Backend-only work first — no infrastructure required, all reversible, all testable locally. Hosting and the domain mapping happen last, only once the thing being hosted is finished. Cloud Run is not started until GCP credits land.

01

Agent Registry

Gap → build

A backend-served catalog of the fleet, replacing the hardcoded frontend array — the literal answer to "how does an org discover your agents."

Pillar 1 · Who
  • GET /agents — id, version, category, schedule, status, served live from masova-enterprise-fleet
  • Mirrors and replaces the static agentCatalog.ts already in the manager frontend
02

Agent Identity

Gap → build

Per-agent scoped credentials, replacing the single shared trigger key across all seven ops routes — the zero-trust half of the rubric's Agent Identity line.

Pillar 1 · Who
  • Per-agent auth scope, verified in main.py trigger routes
  • Demo proof point: a wrong-scope call gets rejected, live, on camera
03

Reasoning-chain observability

Partial → extend

Upgrades runtime/audit.py from outcome-logging to a structured trace of the tool calls and rationale behind each decision — informed by the hash-chained, tamper-evident audit ledger already proven in eu-ai-assurance-os.

Pillar 3 · Behaving
  • Structured tool-call trace captured per run, not just final outcome
  • Existing rationale field on ActionProposal becomes the seed for the full trace
  • Hash-chain pattern adapted from AuditChainHasher for tamper-evidence
04

Model Armor–lite

Gap → build

A guardrail pass on the chat agent's input and output — prompt-injection pattern checks, PII screening before logging. Doesn't need to be Google's product, needs to demonstrably screen.

Pillar 3 · Behaving
  • Input screen before the LLM call, output screen before the response returns
  • Demo proof point: an adversarial prompt gets caught on camera
05

Demo data layer

Gap → build

A seeded SQLite store behind a DEMO_MODE flag, standing in for the platform backend — sidesteps the known backend_tools.py API drift and gives the demo a real database to show before/after row changes against. Seed set: 18 scenarios across all 8 agents, grounded in the platform's real field shapes (confirmed against shared-models, not the drifted fixture assumptions), Paris/EUR market.

Pillar 2 · Allowed
  • Same agent code path, fixture data source instead of the live platform
  • Satisfies the judging bar: "proof of live execution — database updates or UI changes"
  • Corrects real drift found in backend_contracts.py along the way: price not unitPrice, minimumStock not reorderLevel, nested loyaltyInfo/orderStats not flat fields, no APPROVED refund status (approval flows straight to INITIATED by design)
06

Proposal review UI

80% built → wire the rest

The existing manager frontend already has auth, AIAgentsSection.tsx, and a chat + trigger API slice — it's missing the one view that matters most: approving or rejecting a pending proposal.

Pillar 2 · Allowed
  • GET /agent/proposals + resolve mutations added to agentApi.ts
  • Approve / reject panel in AIAgentsSection.tsx, reusing the existing neumorphic design system
  • Demo proof point: proposal disappears from the pending list on approval — a live UI-change proof
07

Ship: Gemini 3.5 → Cloud Run → domain

Last, in order

Everything above is proven locally first, cheap and fast to iterate. Once stable, point LLM_MODEL at Gemini 3.5 Flash for the public deployment, then host on Cloud Run (after GCP credits land), then map the domain. In that order, not before.

Pillar 1Pillar 2Pillar 3
  • Full local pass on LLM_MODEL/LLM_API_KEY (iteration endpoint)
  • Swap to Gemini — no code changes, the LiteLlm wrapper is why it was built this way
  • Deploy this service to Cloud Run with DEMO_MODE=true after the $150 GCP credit lands
  • Record the demo against the live .run.app/console URL; custom domain optional

Before submitting

What's already decided, and what to still watch

Settled

  • Repo can stay private — grant access to testing@devpost.com and cloudhackathons@google.com
  • No full MaSoVa microservices stack needs hosting — out of rubric scope, real budget risk, real API-drift risk
  • Seeded/mock data is normal, accepted hackathon practice — judges expect sandboxed or mocked access where real access doesn't exist
  • Judges are not required to test a live link — text, images, and video can carry the full evaluation

Still watch

  • Video must show the backend running on Google Cloud — a live Cloud Run moment is non-negotiable, even if the rest is recorded locally
  • Nothing public-facing may name the local iteration provider — including API error strings, not just docs
  • README needs a step-by-step setup guide and an architecture diagram — both required submission components
  • Judging bar is explicit: "proof of live execution — terminal logs, database updates, or UI changes" — the seeded SQLite exists specifically to make this checkable

Explicitly out of scope

masova-voice — not part of this submission

A separate repo, SVamseekar/masova-voice, gives the fleet a voice front-end — browser mic in, masova-enterprise-fleet's chat agent as the brain, spoken reply out. It exists, it's real, and it's staying out of the hackathon build.

Why it's excluded here

  • Today's stack is five local services chained together (Voicebox, n8n, Qdrant, a local embed server, masova-enterprise-fleet) — localhost-only, no auth, explicitly marked demo-only. Too many failure points for a one-take recording.
  • It doesn't move any Enterprise Fleet rubric line — no new registry entry, no new identity, no new audit surface. It's a new input modality on the same governed system, not new governance.
  • Budget and timeline already carry seven build phases; a second hosted service adds deploy surface for zero score.

For the product, past the hackathon, the call is the opposite: keep masova-voice as its own bounded service — different latency profile, different release cadence, isolated blast radius from the agent platform's core reliability — rebuilt on Google's STT/TTS and Vertex AI embeddings, calling masova-enterprise-fleet's hosted /agent/chat the same way any other client would. That rebuild is future work, tracked separately from this plan.
